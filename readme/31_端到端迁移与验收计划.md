# 端到端迁移与验收 Implementation Plan

> **For agentic workers:** REQUIRED: Use `superpowers:subagent-driven-development` 或
> `superpowers:executing-plans` 逐任务执行；每个 Task 独立完成证据采集、验证和审查。

**Goal:** 以可复核证据逐能力完成旧构建系统到 `st.build` 的隔离双跑、客户端兼容、平台灰度、故障演练和可回滚切换。

**Architecture:** 迁移验收不创建另一套生产流水线。自动化 harness 只读取固定输入快照、旧系统隔离副本产物和新系统产物，使用结构化 comparator 生成不可变证据；所有真实构建仍通过各阶段受控探针，生产切换由显式审批门禁完成。

**Tech Stack:** Python 3.10、pytest、SHA256、旧客户端 parser、Unity/Android/iOS/Windows 受控节点、ObjectStore/CAS、Markdown/JSON 证据。

---

## 1. 状态、授权边界与完成定义

- 文档状态：**迁移与验收计划完成，独立审查通过**。
- 代码状态：**规划中；当前只有阶段 1/2 领域内核通过自动化门禁**。
- 本文不授权生产切换、SVN 写入、CDN 激活、应用商店上传、证书使用或旧系统运行。
- 旧参考目录 `F:\proj_se\develop\client\tools\build` 永远只读，且禁止作为旧系统双跑工作目录。
- 旧系统双跑前必须复制到批准的隔离根，写入来源 revision/树 hash marker，使用固定输入快照、
  测试凭据和隔离输出/存储前缀；任何 guard 不满足立即失败。

“代码完成”“自动化验收通过”“平台验收通过”“迁移验收通过”和“生产已切换”是五个独立状态。
某能力只有同时具备需求映射、自动化门禁、真实环境证据、差异处置、回滚演练和责任人审批，才能
标记迁移验收通过；生产切换还需单独变更审批，本文本身不构成审批。

## 2. 验收结构与证据目录

```text
tests/migration/
  guard.py                  # 隔离旧副本与输入快照守卫
  legacy_capture.py         # 经审批的旧产物记录读取与完整性校验
  inventory.py              # 能力/输入/工具链清单
  evidence.py               # 规范 evidence manifest 与 SHA256
  protocol_compare.py       # 七个客户端协议文件比较
  artifact_compare.py       # 逻辑路径、hash、size、dependency 比较
  package_compare.py        # Android/iOS/Windows 契约比较
  performance_compare.py    # 同输入耗时/资源统计
  test_*.py                 # 各能力验收
readme/evidence/migration/
  00_能力验收矩阵.md
  01_输入与环境清单.md
  02_客户端协议双跑.md
  03_资源与发布双跑.md
  04_客户端包体双跑.md
  05_故障与恢复演练.md
  06_性能与容量基线.md
  07_灰度与回滚记录.md
  manifests/                # 脱敏 JSON evidence manifests
```

证据 manifest 记录 schema、能力 ID、输入 snapshot/revision、旧/新工具链、命令摘要、环境、开始/结束
时间、产物 SHA256/size、比较器版本、差异、退出码和人工结论引用。SecretRef 值、证书/私钥、用户路径、
未脱敏日志和生产 URL 不进入仓库。

迁移 harness 永远不启动旧 controller/package/upload/signing 入口。旧协议、资源和包体必须由另一个
经审批的受控探针在隔离副本中生成；探针输出 `LegacyCaptureRecord`，记录审批引用、guard 结果、输入
inventory ID、隔离根摘要、工具链、产物 BlobRef 和日志 locator。harness 只接收经 factory 重算 ID、
通过 SHA256/size 校验且输入 inventory 完全相同的 capture。没有旧 capture 时验收保持 `PENDING`。

## 4. 比较规则与差异处置

- 协议首先做原始 bytes diff，再做 parser DTO 语义 diff；换行等已批准差异必须绑定策略版本和客户端验证。
- 资源比较逻辑路径、原始 SHA256/MD5（仅兼容字段）、size、AB 有序重复依赖、Redirect、分包和 variant。
- 发布比较完整 snapshot、传输对象、FileListNo/object_version、远端 hash、CAS generation 与回滚目标。
- 包体不要求签名时间戳或压缩容器字节相同；比较包名/bundle ID、版本、架构/ABI、资源入口、权限、
  SDK 结构、签名有效性、符号映射、安装与启动行为。
- 安全修复造成的预期差异（如 SHA-256 签名、秘密移除）不能用旧字节一致作为目标，但必须有安全审查和功能验证。
- 每个差异分类为 `IDENTICAL`、`EXPECTED`、`BLOCKING`；`EXPECTED` 需要规则 ID、原因、批准人和验证证据，
  不能用自由文本忽略模式批量放行。

## 5. 灰度、观测与回滚

灰度顺序固定为：本地 fixture -> 假外部系统 -> 隔离真实系统 -> 内部测试 profile -> 小比例非关键 job ->
扩大非生产范围 -> 经审批生产。每一级必须观察成功率、耗时、缓存命中、Unity/工具失败、协议 diff、
上传/CAS 冲突、包体安装/启动和恢复时长。

切换开关必须按明确能力/profile 定位，默认旧系统；不能同时让旧新系统写同一生产入口。影子运行只允许
新系统写隔离前缀。回滚以已验证 ReleaseBundle/PackageManifest/配置版本为单位；不得删除新旧不可变产物，
不得把“重新完整构建”作为唯一回滚方案。发生协议、签名、启动、数据丢失或不可判定发布状态时立即停止扩大灰度。

## 7. 失败排查与最终完成标准

| 症状 | 首查证据 |
| --- | --- |
| 双跑输入不一致 | inventory ID、source/resource revision、baseline/toolchain |
| 协议 bytes 不同 | EOL/策略版本、DTO diff、旧 parser 结果 |
| 资源缺失 | BuildManifest、旧快照、逻辑路径 ownership |
| 灰度发布冲突 | ReleaseBundle、expected/current generation、写入前缀 |
| 包体行为不同 | 平台 validator、安装/启动日志、SDK descriptor |
| 无法回滚 | 历史 bundle/package/config、CAS 记录、回滚演练 |

最终完成是能力矩阵中目标范围逐项具有可复核证据，生产切换经过独立审批且回滚演练有效。任何一项
未关闭都只表示局部能力尚未迁移，不得把文档完成、单元测试通过或一次真实构建成功写成全系统完成。
