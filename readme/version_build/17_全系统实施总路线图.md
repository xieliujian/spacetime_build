# 全系统实施总路线图

## 1. 文档状态

- 文档状态：**设计完成，独立审查通过，待用户审阅**。
- 实现状态：**第一阶段工程骨架和第二阶段纯 Python 领域内核已完成；第三阶段实施计划已完成但代码尚未开始；第四阶段及以后均为规划中**。

- 本文不得作为运行命令说明；仓库当前仍没有可执行的构建、发布或迁移 CLI。

## 2. 目标

本文为 `spacetime_build` 后续全部设计和实施文档提供唯一总入口，解决以下问题：

1. 明确旧系统每类能力在新系统中的目标归属；
2. 固定兼容协议、外部集成、资源、发布、CLI、Android、iOS 和辅助模块之间的依赖顺序；
3. 统一“设计完成”“代码完成”“自动化验收通过”和“迁移验收通过”的含义；
4. 把全系统拆为能够独立设计、测试、审查和交付的子项目；
5. 保证所有未实现能力始终明确标记为规划中，避免文档先于代码宣称可用；
6. 为逐阶段 TDD 实现提供稳定的文档路由和证据要求。

最终目标是在不修改旧目录 `F:\proj_se\develop\client\tools\build` 的前提下，重新实现：

- 旧客户端可见资源协议；
- 资源构建与 AssetBundle 生成；
- 确定性发布、缓存、恢复、激活和回滚；
- Android APK/AAB 构建；
- iOS Xcode/IPA 构建；
- Windows 客户端构建；
- IL2CPP、SDK、分支和美术辅助能力；
- 可审计的 CLI、日志、状态和端到端迁移验收。

## 3. 非目标与安全边界

### 3.1 非目标

本文不包含任何功能实现，不替代各子系统的详细设计和实施计划，也不承诺阶段日期。
各阶段工作量和外部环境由实际 fixture、Unity 版本、平台节点和迁移证据决定，不使用完成百分比推测进度。

### 3.2 旧系统边界

- `F:\proj_se\develop\client\tools\build` 只允许读取和分析；
- 禁止修改旧目录中的脚本、配置、证书、资源或工具；
- 禁止从旧目录直接运行可能写文件、提交 SVN、调用 Jenkins、上传资源或签名包体的入口；
- 旧系统双跑必须先复制到隔离工作区，并使用不可变输入快照；
- 复制范围、输入 SHA256、执行命令、退出码和输出 SHA256 必须写入迁移证据；
- 新代码、测试和文档只写入当前仓库。

### 3.3 凭据与平台边界

- SVN、Jenkins、CDN、签名和证书凭据不得写入源码、fixture、日志或构建清单；
- Android keystore、iOS 证书和 provisioning profile 只通过受控凭据引用接入；
- iOS 的真实 Xcode、签名和 IPA 验收只能在受控 macOS 节点执行；
- 本地开发机上的替身测试不能替代真实 Android、iOS 或 Windows 包体验收。

## 4. 文档优先级与职责

发生冲突时按以下顺序处理：

1. 根目录 `AGENTS.md`：仓库级安全、编码、测试和文档约束；
2. `readme/version_build/00_全新构建系统设计.md`：全系统架构、不变量和目标协议；
3. 本文：子项目边界、实施依赖和统一状态门禁；
4. 当前阶段设计文档：模块职责、接口、数据流和失败语义；
5. 当前阶段实施计划：精确文件、TDD 步骤、验证命令和交付清单；
6. 证据文档：真实执行环境、输入输出摘要、diff、解析和包体验证结果；
7. README 与交接文档：只汇总已经由上述材料证明的当前状态。

若计划与已实现代码不一致，必须先把状态标为不一致并核对代码和测试；不得仅通过修改 README 把规划能力描述为已完成。

## 5. 统一状态模型

所有主要能力和阶段只使用以下状态：

| 状态 | 含义 | 最低证据 |
| --- | --- | --- |
| 规划中 | 已列入路线图，但设计或实现未开始 | 本文中的能力项 |
| 设计中 | 正在确认职责、接口、流程和验收标准 | 设计文档草稿 |
| 设计完成 | 设计已审查，可编写实施计划 | 已批准的设计文档 |
| 实施计划完成 | TDD 任务、文件和验证命令已审查 | 已批准的实施计划 |
| 实现中 | 至少一个计划任务已开始，阶段总门禁未关闭 | 失败测试或进行中的任务记录 |
| 代码完成 | 计划内生产代码已实现，但可能仍缺平台或迁移证据 | 目标测试和代码审查记录 |
| 自动化验收通过 | 完整测试、覆盖率、Ruff、Pyright、compileall 和文档检查通过 | 最新命令、退出码和摘要 |
| 平台验收通过 | 真实外部系统或目标平台产物已验证 | Unity、Android、iOS、CDN 等环境证据 |
| 迁移验收通过 | 新旧双跑、兼容验证、灰度和回滚要求全部关闭 | 可复核的迁移证据 |

约束：

- “文档已写”最多表示设计或实施计划完成；
- “单元测试通过”不能表示平台验收通过；
- “新 parser 可读取”不能替代旧客户端 parser 验证；
- Android/iOS 只有生成并检查真实 APK、AAB 或 IPA 后才能标记平台可用；
- 任何缺少必需证据的阶段必须保持在较低状态。

## 7. 目标模块边界

目标模块按稳定依赖方向拆分：

```text
cli
  -> application
       -> core
       -> compatibility
       -> resource
       -> release
       -> package
       -> ports
            <- integrations
       -> services
       -> sdk
       -> branch
       -> art
```

各单元职责如下：

| 单元 | 负责 | 不负责 |
| --- | --- | --- |
| `core` | 领域对象、任务协议、DAG、身份、执行和构建记录 | Unity、SVN、上传和平台打包 |
| `ports` | 外部系统的稳定 Protocol 和类型化请求/结果 | 具体命令、网络库和供应商细节 |
| `integrations` | SVN、Unity、Jenkins、存储/CDN、进程和凭据适配 | 业务规划和旧协议拼接 |
| `compatibility` | 六字段文件列表、五库、Redirect、分包和 CDN 布局协议 | 构建资源、上传对象和状态变更 |
| `resource` | 各资源 Task、AB 清单采集、低清资源和资源级校验 | 发布激活、渠道 SDK 和包体签名 |
| `release` | 快照合并、传输对象、缓存、上传计划、验证、激活和回滚 | Unity 资源生成和客户端包体构建 |
| `package` | Unity Player 导出、Android/iOS/Windows 包体计划和产物校验 | 兼容协议和资源发布策略 |
| `services` | IL2CPP 等可复用构建服务 | 渠道业务编排 |
| `sdk` | 渠道 SDK 配置、合并和平台扩展 | 基础平台构建器 |
| `branch` | 分支相关构建配置和版本映射 | SVN 客户端实现 |
| `art` | 美术辅助检查和可复用处理任务 | 资源发布与客户端协议 |
| `application` | 组合用例、事务边界和阶段编排 | 直接调用 shell 或拼接协议文本 |
| `cli` | 参数、配置覆盖、命令路由和用户可见退出码 | 领域规则和具体外部系统实现 |

每个模块必须可以用替身端口和临时目录独立测试。外部副作用只能经 `ports` 和 `integrations` 发生。

## 8. 全系统数据流

### 8.1 资源构建与发布

```text
CLI/config
  -> 固定源码与资源 revision
  -> 创建隔离工作区
  -> 资源 BuildTask.plan
  -> BuildPlanner / BuildGraph
  -> Unity 或纯 Python Task.execute
  -> 产物校验与内容寻址存储
  -> BuildManifest
  -> 与 BaselineReleaseBundle 合并完整快照
  -> Redirect / 分包 / 传输对象规划
  -> ReleaseManifest / ReleaseBundle
  -> 旧客户端协议生成与验证
  -> 对象上传和远端哈希校验
  -> CAS 激活版本入口
```

### 8.2 客户端打包

```text
PackageRequest
  + 已激活或已验证 ReleaseBundle
  + 固定源码 revision
  + 固定 Unity/SDK/IL2CPP 工具链
  -> 隔离 Unity 工程准备
  -> 平台 Player 工程导出
  -> SDK/渠道配置
  -> Android Gradle 或 iOS Xcode 构建
  -> 签名和符号产物收集
  -> 包体结构、版本、资源入口和哈希校验
  -> PackageManifest / PackageExecutionRecord
  -> 可选的受控上传
```

资源发布与客户端出包是两个独立用例。客户端出包必须显式引用一个已验证的发布聚合，不能隐式读取某个可变资源目录作为发布真相。

## 13. 统一质量门禁

### 13.1 每个 TDD 任务

1. 添加能证明目标行为的失败测试；
2. 运行精确测试并确认因缺少目标行为失败；
3. 编写最小实现；
4. 运行目标测试和直接相关回归；
5. 检查中文 docstring、类型和异常边界；
6. 更新当前任务复选框和直接相关文档；
7. 未经用户明确要求不创建 Git commit。

### 13.2 每个阶段自动化门禁

```powershell
python -m pytest -q
python -m pytest --cov=core --cov=release --cov-report=term-missing --cov-fail-under=80
python -m ruff format --check .
python -m ruff check .
python -m pyright
python -m compileall -q src tests
```

同时要求：

- `core`、`release` 及新增主要子包各自覆盖率不低于 90%；
- `tests/quality/test_chinese_documentation.py` 通过；
- 完整测试无非预期 skip；
- 目标 Python 最低版本为 3.10；
- 文档与当前实现一致；
- 工作树中的用户已有改动未被覆盖。

### 13.3 外部与迁移门禁

- Unity：固定版本、固定工程 revision、隔离工作区、命令和日志摘要；
- SVN：只在测试仓库或隔离工作副本验证，记录 revision；
- CDN/对象存储：隔离前缀、远端哈希、失败注入和清理策略；
- Android：APK/AAB 结构、签名、版本、ABI、资源入口、安装和启动；
- iOS：IPA 结构、签名、bundle ID、版本、架构、资源入口、安装和启动；
- Windows：包体结构、版本、架构、资源入口和启动；
- 兼容协议：历史 fixture、新旧字节 diff 和旧客户端 parser；
- 发布：并发冲突、CAS、部分上传、重试、激活和回滚。

## 14. 错误处理与恢复原则

- 配置、规划、协议和产物校验错误不重试；
- 网络超时、限流和临时锁只能由适配器按明确策略有限重试；
- Unity、Gradle 和 Xcode 非零退出必须保留命令摘要、退出码和日志位置，并转换为类型化错误；
- 日志不得记录明文凭据、签名密码或完整敏感配置；
- 取消先停止新任务调度，再终止外部进程，最后保留可恢复记录；
- 构建任务和上传操作必须幂等；
- 不得用递归方式重启完整构建流水线；
- 恢复必须重新验证当前规划身份、输入 revision、工具链、输出哈希和基线聚合；
- 客户端出包失败不得改变已激活资源版本；
- 发布激活失败不得把未验证对象暴露为当前版本。
