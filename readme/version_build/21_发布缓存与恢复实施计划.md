# 发布、缓存与恢复 Implementation Plan

> **For agentic workers:** REQUIRED: Use `superpowers:subagent-driven-development` 或 `superpowers:executing-plans` 执行。每个 Task 独立完成 RED、GREEN 和回归。

**Goal:** 从 BuildManifest 和不可变基线生成完整 ReleaseBundle，并实现 Redirect、分包、传输对象、缓存、上传验证、CAS 激活、恢复和回滚。

**Architecture:** 规划器保持纯 Python；Blob/cache/object store 经端口；旧协议只由 compatibility writer 生成；上传对象全部验证后才能推进现有激活状态机。

**Tech Stack:** Python 3.10、现有 `release`、阶段 3 compatibility、阶段 4 storage ports、pytest。

## 2. 文件结构

```text
src/release/
  merger.py              # BuildManifest + baseline -> 完整 snapshot
  redirect.py            # Redirect 规划
  redirect_container.py  # 确定性容器字节
  subpackage.py          # membership -> bit flag
  transfer.py            # 原始/zip 传输对象
  cache_keys.py          # 规范 cache key
  cache_store.py         # 缓存读取、验证和损坏废弃
  assembly.py            # ReleaseManifest/Bundle 组装
  protocol_outputs.py    # compatibility writer 输出登记
  upload_plan.py         # 上传顺序和必要对象集合
  uploader.py            # 幂等对象上传
  remote_verifier.py     # 远端哈希证明
  activator.py           # CAS 激活
  recovery.py            # 发布恢复决策
  rollback.py            # Bundle 级回滚
```

## 3. 类型化入口与数据流

```text
BuildManifest + baseline
  -> SnapshotMerger
  -> RedirectPlanner -> RedirectContainerBuilder
  -> SubpackagePlanner
  -> TransferObjectBuilder -> cache
  -> ReleaseManifest/Bundle factory
  -> compatibility writers
  -> UploadPlan -> uploader -> RemoteVerifier
  -> CAS Activator
```

配置、规划、协议和哈希错误不重试；上传临时失败可有限重试；CAS 冲突不重试并返回冲突状态。取消停止新上传，已上传不可变对象保留并可在恢复时复核。
本阶段不引入单体 `ReleasePlanner`/`PlannedRelease`；计划 26 的 application 用例按上图组合各单职责服务。CAS 的 `expected_generation` 始终复用现有整数语义。

## 10. 失败排查与后续入口

| 症状 | 首查证据 |
| --- | --- |
| 快照缺文件 | BuildManifest、baseline ID、目录所有权日志 |
| Redirect 偏移错误 | 策略版本、桶顺序、容器 SHA256 |
| 分包异常 | membership、Redirect 容器路径、最终 flag |
| 上传后无法激活 | UploadPlan、必要对象、远端证明、CAS generation |
| 恢复重复上传 | execution record、对象摘要、uploader 幂等记录 |
| 回滚冲突 | 当前 generation、目标 Bundle ID、并发发布记录 |

自动化通过后计划 26 可编排发布用例，计划 22/24/27 可引用已验证 ReleaseBundle。真实存储与兼容证据关闭前，不得宣称生产发布可用。
