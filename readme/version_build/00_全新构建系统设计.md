# 全新构建系统设计

## 1. 目标

在不修改原始目录 `F:\proj_se\develop\client\tools\build` 的前提下，将核心构建能力迁移到当前工程，并进行全新架构设计。

新系统允许重构 Jenkins 调用方式、配置方式、任务生命周期、缓存、发布和错误处理。唯一必须保持兼容的是客户端可见协议：

- AssetBundle 相对路径；
- `assetbundledb_*.txt`；
- 六字段文件列表；
- Redirect 名称、偏移和长度；
- 分包 bit flag；
- CDN 版本目录和版本入口语义。

## 2. 技术约束

- Python 3.10+；
- 导入命名空间使用小写 `st.build`；
- 包、模块、函数和变量使用 `snake_case`；
- 类和异常使用 `PascalCase`；
- 常量使用 `UPPER_SNAKE_CASE`；
- 路径统一使用 `pathlib.Path`；
- 公开 API 必须有类型标注；
- 所有源码模块、类、异常、函数和方法必须提供详细中文 docstring；
- 复杂算法、兼容协议、边界条件、异常分支和外部副作用必须有中文行内注释；
- 注释重点解释职责、设计原因、约束和副作用，不编写逐行复述代码的无效注释；
- 禁止模块导入时执行构建；
- 禁止业务层直接调用 `os.system`；
- 原始目录全程只读。

## 3. 总体架构

```text
st/build/
├─ core/                    # 配置、领域模型、任务图、执行器、异常
├─ integrations/            # SVN、Unity、Jenkins、CDN 等适配器
├─ compatibility/           # 旧客户端协议模型、序列化和契约校验
├─ release/                 # 发布聚合、基线合并、激活和回滚
├─ resource/
│  ├─ tasks/                # 场景、角色、Shader、UI 等资源任务
│  ├─ assetbundle/          # AB 数据库、依赖与 Redirect
│  └─ subpackage/           # 分包领域逻辑
├─ package/
│  ├─ preparation/          # Unity 工程准备
│  └─ platforms/            # Android、iOS、Windows
├─ services/il2cpp/
├─ sdk/
├─ branch/
├─ art/
└─ cli/
```

系统分为五层：

1. **领域模型**：构建请求、任务、产物、依赖和发布版本；
2. **计划层**：根据配置生成任务 DAG，检查循环依赖和输出冲突；
3. **执行层**：调度任务、使用缓存并记录状态；
4. **集成层**：隔离 SVN、Unity、Jenkins 和云存储；
5. **兼容层**：将内部结构化产物转换为旧客户端协议。

依赖方向固定为：

```text
cli → application → domain
                  ↘ ports ← integrations
                  ↘ compatibility
                  ↘ release
```

领域层不导入集成层、兼容层或平台实现。兼容序列化不负责网络上传，发布计划不直接操作具体云存储。

## 4. 构建生命周期

```text
BuildRequest
  → BuildPlanner
  → BuildGraph
  → TaskExecutor
  → ArtifactRegistry
  → BuildManifest

ReleaseRequest + BuildManifest + BaselineReleaseBundle
  → SnapshotMerger
  → RedirectPlanner
  → SubpackagePlanner
  → TransferObjectPlanner
  → ReleaseManifest
  → ReleaseBundle
  → LegacyProtocolWriter
  → ReleasePublisher
```

构建阶段：

1. 加载并校验配置；
2. 获取指定版本源代码和资源；
3. 生成任务图；
4. 按依赖执行任务；
5. 收集 Unity manifest 和其他产物；
6. 执行构建产物校验；
7. 生成不可变 `BuildManifest`。

发布阶段：

1. 加载 `BuildManifest`、基线版本和发布配置；
2. 合并完整资源快照；
3. 生成 Redirect、分包和传输对象；
4. 生成不可变 `ReleaseManifest` 和 `ReleaseBundle`；
5. 从已验证发布快照生成并校验客户端兼容协议；
6. 上传并验证所有对象；
7. 最后以 CAS 更新版本入口。

构建与发布完全分离：

- `BuildRequest` 描述源码、工具链和需要构建的资源；
- `BuildManifestPayload` 只记录可复现的构建产物，不包含 CDN URL、发布版本号、唯一执行 ID、运行状态、耗时或 `manifest_id`；
- `BuildManifest` 只能由工厂从 `BuildManifestPayload` 创建；工厂对 payload 的规范字节计算 `manifest_id`，构造后 payload 与 ID 均不可变，不允许公开构造空 ID 或陈旧 ID 的 manifest；
- `ReleaseRequest` 描述目标环境、版本号、基线版本和发布策略；
- `ReleaseManifest` 记录单个资源变体的协议无关完整发布快照和传输对象，不包含客户端文本 DTO 或可变激活状态；
- `ReleaseBundle` 是不可变发布聚合，包含 main manifest 和可选 low manifest，并共享同一个 `FileListNo`；
- `BuildExecutionRecord` 单独记录 `schema_version`、唯一 `build_id`、构建状态、耗时和日志，未知 schema 必须拒绝；
- `ReleaseActivationRecord` 单独记录 `schema_version`、上传、验证、激活、冲突和回滚状态，未知 schema 必须拒绝。

已有 `BuildManifest` 可以生成多个 `ReleaseBundle`，不需要重新运行 Unity。

局部构建必须指定一个不可变的 `BaselineReleaseBundle`。主、低清变体分别与基线 Bundle 中对应的 manifest 合并；低清可以显式继承主版本允许共享的产物。`SnapshotMerger` 按资源目录所有权合并新增、替换和删除项，并产生完整快照。并发发布不能隐式合并：发布时基线 Bundle 代际必须仍为当前代际，否则要求重新规划。激活、回滚和审计均以 Bundle 为最小单位。

## 5. 任务模型

资源任务通过统一协议接入：

```python
class BuildTask(Protocol):
    @property
    def name(self) -> str: ...

    def plan(self, context: BuildContext) -> TaskPlan: ...

    def execute(
        self,
        context: BuildContext,
        inputs: ArtifactCollection,
    ) -> TaskResult: ...
```

每个任务声明：

- 输入文件和上游产物；
- 输出逻辑路径；
- 平台和工具链要求；
- 是否支持缓存；
- 是否允许并行；
- 任务实现版本。

任务规划采用单一路径：应用层先对每个 `BuildTask` 调用 `plan(context)` 得到完整不可变 `TaskPlan` 集合，`BuildPlanner.plan(plans, context)` 只消费这些已完成计划，不再接收 `TaskSpec`。`TaskIdentity.from_plan(plan, context, upstream_identities)` 按拓扑顺序生成当前规划的 expected identity；`BuildGraph`、Planner、Frontier 和 Executor 都引用同一 `TaskPlan`，禁止同时存在 `from_spec` 与 `from_plan` 两套身份来源。

任务不能直接提交 SVN、触发 Jenkins 或上传 CDN。外部副作用只允许发生在明确的集成和发布阶段。执行器收到 `TaskResult` 后必须在登记产物前验证实际输出逻辑路径与 `TaskSpec.outputs` 严格相等；缺失输出、未声明输出和重复输出全部视为 `ArtifactValidationError`。

## 6. 配置模型

运行配置使用 TOML，命令行参数可以覆盖配置。密钥只能通过环境变量或密钥服务引用。

```toml
[build]
profile = "android_release"
resources = ["config", "shader", "scene", "character", "ui"]
max_workers = 4

[toolchain]
unity_version = "2022.3.62f2"

[source]
provider = "svn"
revision = "HEAD"

[publish]
target = "production"
subpackage = true
redirect = true
```

配置优先级：

```text
命令行参数 > 环境变量 > build.toml > 默认值
```

配置在进入业务层前转换为不可变数据类。无效平台、资源类型、Unity 版本和发布目标必须在启动阶段失败。

## 7. 内部产物模型

内部使用职责明确的多种不可变对象：

```python
@dataclass(frozen=True)
class BlobRef:
    locator: str
    sha256: str
    size: int

@dataclass(frozen=True)
class LogicalArtifact:
    logical_path: str
    kind: ArtifactKind
    blob: BlobRef
    dependencies: tuple[str, ...]
    subpackage_ids: frozenset[int]
    metadata: ArtifactMetadata

@dataclass(frozen=True)
class RedirectSlice:
    container_logical_path: str
    container: BlobRef
    offset: int
    length: int

@dataclass(frozen=True)
class ReleaseEntry:
    logical_path: str
    variant: ResourceVariant
    source_blob: BlobRef
    source_md5: str
    original_size: int
    transfer_blob: BlobRef
    transfer_size: int
    list_version: int
    object_version: str
    file_url: str
    subpackage_flag: int
    object_origin: ReleaseObjectOrigin

@dataclass(frozen=True)
class ReleaseSnapshotEntry:
    release_entry: ReleaseEntry
    artifact_class: ReleaseArtifactClass
    memberships: frozenset[ReleaseMembership]
    assetbundle_dependencies: tuple[str, ...]
    redirect_slice: RedirectSlice | None

@dataclass(frozen=True)
class ReleaseSnapshot:
    variant: ResourceVariant
    entries: tuple[ReleaseSnapshotEntry, ...]
```

`BlobRef.locator` 指向持久化内容寻址存储，不能引用临时工作目录。原文件、zip 传输对象和 Redirect 容器分别具有独立的哈希与大小。

`ResourceVariant` 只在 release entries 模块声明，snapshot、manifest、bundle 和 compatibility 均从该模块导入，禁止重复枚举。`ReleaseSnapshot` 锁定一个 variant，所有 entry 的 variant 必须一致；`ReleaseManifest` 的 variant 也必须与 snapshot 一致。

`ReleaseSnapshot` 是协议无关的完整发布快照。它用 `assetbundle_dependencies` 保留 Unity manifest 的原始有序重复语义，用 `RedirectSlice` 表达容器逻辑路径、Blob、偏移和长度，并校验依赖目标与 Redirect 容器均存在于快照。`ReleaseArtifactClass` 区分 `REGULAR_FILE`、`ASSET_BUNDLE`、`REDIRECT_SLICE`、`REDIRECT_CONTAINER`，`ReleaseMembership` 显式声明 `FILE_LIST` 与 `ASSET_BUNDLE_DATABASE` 成员资格：

- 普通文件只进入文件列表；
- 未 Redirect 的原始 AB 同时进入文件列表和 AB 数据库；
- 被 Redirect 替代的原始 AB 以 `REDIRECT_SLICE` 只进入 AB 数据库，不进入文件列表；
- Redirect 容器同时进入文件列表和 AB 数据库，并按逻辑路径恰好出现一次；
- 非 AB 条目禁止进入 AB 数据库。

compatibility 层只能按上述 membership 从已验证的 `ReleaseSnapshot` 单向生成 DTO，不能通过任意公开构造器绕过领域校验。

`object_version` 是受约束的单个路径段，不允许 `/`、`\`、`.` 或 URL 转义字符。主版本本次新上传对象使用当前十进制正整数，低清本次新上传对象使用 `{当前正整数}_low`；从基线继承且未变化的 `ReleaseEntry` 标记为 `HISTORICAL`，可以保留历史 `object_version` 和 `file_url`。`ReleaseBundle` 只校验本次新上传对象的当前版本后缀，不得拒绝历史条目。

发布身份与构建 manifest 使用相同的 payload/factory 原则：

- `ReleaseManifestPayload` 持有 schema、单一 variant、当前 FileListNo、完整 snapshot 和来源 BuildManifest IDs，不含 manifest ID；
- `ReleaseManifestFactory` 规范化无序 snapshot entry/source ID 输入、保留有序重复依赖并自动计算不可变 ID；
- `ReleaseBundlePayload` 持有 schema、无序 manifest 集合和可选 baseline bundle ID，不含 bundle ID；
- `ReleaseBundleFactory` 校验一个 main、至多一个 low、共享 FileListNo 后自动计算不可变 ID；
- 两类反序列化都必须重算 ID，拒绝空 ID、陈旧 ID、未知 schema 和 variant 不一致，禁止公开直接构造。

每次构建生成带 schema 版本的 `artifact-manifest.json`，包含：

- 确定性 `manifest_id`、输入版本和配置摘要；
- 任务实现版本和工具链版本；
- 产物哈希、大小和来源任务；
- AB 依赖和 Redirect 映射；
- 分包归属；
- 确定性的构建产物及其来源。

读取 manifest 时必须先解析 `BuildManifestPayload`，再由工厂重算 ID 并与文件中的非空 `manifest_id` 严格比较；空 ID、陈旧 ID 或内容不匹配都必须拒绝，不能返回可被业务层使用的 `BuildManifest`。

所有逻辑路径必须是 `/` 分隔、区分大小写、无 `..` 的受约束相对路径。metadata 使用类型化结构，不接受任意 `Mapping[str, object]`。

## 8. 客户端兼容层

旧协议集中由以下转换器生成：

- `LegacyAssetBundleDbWriter`；
- `LegacyFileListWriter`；
- `LegacyRedirectWriter`；
- `LegacySubpackageEncoder`；
- `LegacyCdnLayoutPublisher`。

新业务代码不得直接拼接旧文本格式。文件列表 DTO 只能从 `ReleaseEntry`/`ReleaseManifest` 转换，AssetBundle 数据库 DTO 只能从已验证的 `ReleaseSnapshot` 转换；兼容 DTO 不提供绕过领域校验的任意公开构造入口。转换器使用 Golden 测试保证输出稳定，并验证旧客户端所需的排序、索引、编码和路径规则。

### 8.1 AssetBundle 数据库契约

- UTF-8 编码，不写 BOM；
- 换行由版本化兼容策略指定；迁移 fixture 必须确认 Windows CRLF 与 macOS LF 的旧产物差异，任何统一换行改动都需客户端解析验证和兼容性决策；
- AB 名按字节序升序排列并分配从 0 开始的稳定索引；
- 首行为 `{ab_name}\t{index}`；
- 依赖行为 `\tDepend:` 后跟按数据库索引编码的 Tab 分隔列表；
- Redirect 行为 `\tRedirect:{container_index}\t{offset}\t{length}`；
- 空依赖和空 Redirect 不输出对应行；
- 所有依赖和 Redirect 目标必须存在；
- 输出前执行循环依赖检测。

### 8.2 六字段文件列表契约

每行固定六列：

```text
FileName<TAB>FileVersion<TAB>FileSize<TAB>FileMD5<TAB>FileUrl<TAB>FileSubpackID
```

- 按 `FileName` 升序输出；
- `FileName` 使用 `/` 和原有大小写；
- `FileMD5` 是原始逻辑文件 MD5；
- 未压缩文件的 `FileSize` 是原文件大小；
- zip 文件的 `FileSize` 是传输 zip 大小，但 MD5 仍为原始文件 MD5；
- 列表中的 `FileVersion` 使用当前 `list_version`；组装 `ReleaseManifest` 时每个
  `ReleaseEntry.list_version` 必须与 manifest 的 `FileListNo` 相等。未变化文件的
  `FileUrl` 和 `object_version` 可以继续指向历史内容对象；
- 完整发布列表中的 `FileVersion` 必须在 `1..Int32.MAX_VALUE`，0 保留给旧客户端删除语义；
- `FileSize` 和 `FileSubpackID` 必须在 `0..Int32.MAX_VALUE`；
- `FileUrl` 严格等于
  `urllib.parse.quote(f"{object_version}/{FileName}", safe="/")` 的结果，zip
  传输对象追加 `.zip`；历史对象使用自身历史 `object_version`；
- `config/` 和文件名包含 `assetbundledb_` 时压缩；非 trunk 的 Windows `config/` 不压缩；
- 重复文件名、字段数错误和非法整数必须失败。
- 只序列化具有 `ReleaseMembership.FILE_LIST` 的快照条目；被 Redirect 替代的原 AB 不进入文件列表，Redirect 容器按逻辑路径恰好出现一次。

### 8.3 Redirect 契约

- `scene`：100 KiB；排除 `-stream.assetbundle` 和包含 `_dependdb.assetbundle` 的文件；普通/base/baseback 前缀分别为 `scene/redirect/`、`scene/redirect_base/`、`scene/redirect_baseback/`，桶数分别为 31、61、41；
- `story`：200 KiB；普通/base 前缀分别为 `story/redirect/`、`story/redirect_base/`，桶数均为 7；
- `ui`：200 KiB；排除 `ui/extend.assetbundle`、`ui/ui_prepare_data.assetbundle`；普通/base 桶数分别为 51、11；
- `texture`：200 KiB；排除 `texture/icon/icondatabase.assetbundle`；普通/base 桶数分别为 51、7；
- `character`：200 KiB；排除 `character/characterdatabase.assetbundle`、`character/character_gpuskin_dependdb.assetbundle`、`character/character_expression.assetbundle`；普通/base 桶数分别为 51、17；
- `particle`：200 KiB；排除 `particle/particle_dependdb.assetbundle`；普通/base 桶数分别为 51、17；
- ui、texture、character、particle 的前缀均沿用 `{type}/redirect/` 和 `{type}/redirect_base/`；
- 使用逻辑路径 SHA1 取模分桶；
- 每个桶内按逻辑路径升序拼接，确保偏移稳定；
- Offset 为容器内起始字节，Length 为原始 AB 字节数；
- 原始 AB 在发布快照中替换为 Redirect slice，容器作为独立 Blob 发布；
- 阈值、排除项和桶数量写入带版本的兼容策略，变更必须提升协议策略版本。

### 8.4 分包契约

- `0` 表示 INSTALL，不设置 bit；
- 正数 ID 使用 `1 << (id - 1)`；
- 多包归属使用按位 OR，不使用算术假设；
- INSTALL 优先于所有其他归属，BASE 次之；
- `30` 为 GARBAGE，`31` 为 DONTDOWNLOAD；
- 兼容模式只接受 0 到 31；ID 32 在确认旧客户端无符号解析能力前禁止发布；
- Redirect 后记录容器路径，不记录已被替换的小 AB；
- 非法 ID 和无法解析的基础包配置必须在发布前失败。

### 8.5 CDN 布局契约

- 新上传资源对象位于 `{root}/{branch}/{platform}/data/{job}/{object_version}/{FileName}`；
- 完整文件列表可以把所有行的 `FileVersion` 更新为当前 `list_version`，但未变化行保留历史 `FileUrl`；
- 文件列表位于 `{FileListNo}/{FileListNo}.txt.zip`；
- 低清发布保留 `{FileListNo}_low/` 语义；
- 版本入口中的 `FileListBaseUrl` 和 `FileListNo` 最后更新；
- 路径布局和入口字段由版本化策略对象生成。

### 8.6 AB 数据库归属与顺序

- `scene/` 与 `story/` 写入 `assetbundledb_scene.txt`；
- `ui/` 写入 `assetbundledb_ui.txt`；
- `texture/` 写入 `assetbundledb_other.txt`；
- `character/` 写入 `assetbundledb_character.txt`；
- `particle/` 写入 `assetbundledb_particle.txt`；
- `depend/shader_*.assetbundle` 共享 Shader 依赖复制到上述五个数据库，各数据库
  保持独立索引空间；其他 `depend/` 路径在真实 fixture 证明归属前拒绝发布；
- `skill/` 写入 `assetbundledb_other.txt`；
- `lingren/resources/global/` 写入 `assetbundledb_scene.txt`；
- AB 记录按名称排序；依赖列表严格保持 Unity manifest 的原始顺序和重复语义，除非真实历史 fixture 证明旧流程会去重；
- 同一 AB 可因共享依赖规则进入多个数据库；每个依赖和 Redirect 容器必须与引用方
  存在于同一数据库，不能跨数据库引用索引；
- 多任务中间数据库可存在，但发布前必须聚合为上述五个客户端数据库。
- 只序列化具有 `ReleaseMembership.ASSET_BUNDLE_DATABASE` 的快照条目；普通非 AB 文件不得进入数据库，Redirect slice 与其容器均按已验证 membership 转换且容器记录恰好一次。

## 9. 缓存与增量构建

缓存键由以下内容确定：

```text
任务实现版本
+ 已解析并固定的全部 SVN revision
+ 基线 BuildManifest/ReleaseBundle ID
+ 输入目录树哈希
+ 影响该任务的配置子集
+ Unity、插件、构建脚本和外部工具版本
+ Python 依赖锁文件哈希
+ 内部 schema、客户端协议策略版本和新系统实现源码/构建包 SHA256
+ 平台
+ 上游产物哈希
```

`HEAD` 只能作为用户输入，规划阶段必须解析为固定 revision 后才能执行。目录树哈希只规范化路径表示：UTF-8 路径、`/` 分隔、大小写敏感；文件内容必须按任务实际读取的原始字节哈希，不能转换换行。符号链接记录链接目标而不隐式展开。缓存元数据采用确定性 JSON 序列化。

缓存只存储不可变产物，不缓存工作目录。缓存命中后仍需验证产物哈希。系统支持禁用缓存、指定任务强制重建和损坏条目自动废弃。

## 10. 错误处理与恢复

异常体系：

```text
BuildError
├─ ConfigurationError
├─ PlanningError
├─ SourceError
├─ ToolExecutionError
├─ ArtifactValidationError
├─ PublishError
└─ CompatibilityError
```

策略：

- 配置、规划和校验错误不重试；
- 网络超时、限流和临时锁最多重试三次；
- Unity 编译失败不递归执行整个流水线；
- 每个任务必须幂等；
- Unity 任务在隔离工作区运行，通过不可变产物提交实现可重放；
- 每个任务状态使用临时文件加原子替换落盘；
- 恢复对象是所有已验证完成节点组成的 DAG frontier，不是“最后一个任务”；
- Frontier 验证 API 必须显式接收当前规划生成的 `task_name → expected TaskIdentity` 映射，逐节点把完成记录身份与 expected identity 比较；
- `CompletedTaskRecord` 保存该节点完整、不可变的 `tuple[LogicalArtifact, ...]`，而不是仅保存 BlobRef；恢复时实际逻辑路径集合必须与当前 `TaskPlan.spec.outputs` 严格相等，并拒绝缺失、未声明和重复路径；
- 恢复前还要重新校验 BuildRequest、固定 revision、工具链、基线、schema、upstream identities，以及每个已记录 LogicalArtifact 的 Blob 实际哈希与大小；
- Frontier 只向执行器返回不可变的 verified reusable set 及其已验证输出；执行器不能接收或自行信任原始完成记录；
- 执行器使用租约防止同一 build ID 被并发恢复；
- 上传阶段记录已完成文件，支持断点续传。

## 11. 事务式发布

发布顺序：

```text
本地 staging
  → 完整校验
  → 上传资源文件
  → 校验远端哈希
  → 上传版本文件列表
  → 最后更新版本入口
```

发布开始时从版本服务预留 `1..Int32.MAX_VALUE` 范围内的唯一 `FileListNo`，所有对象禁止覆盖已有 key。启用低清时，主版本和低清版本组成一个不可变 `ReleaseBundle`，共享同一个 `FileListNo`，分别生成 `{FileListNo}/` 和 `{FileListNo}_low/` 文件列表；两者的必要对象必须全部验证成功后才能激活。

资源与文件列表上传完成后，发布器使用“期望旧代际”条件一次性更新包含主/低清入口的版本记录：

```text
compare_and_swap(expected_generation, new_release_bundle)
```

若入口代际已变化，激活失败且不覆盖其他发布。失败版本保留为未激活 ReleaseBundle，可重试或回收。回滚通过对同一入口执行新的 CAS，将其重新指向已验证的历史 ReleaseBundle。

多个发布目标分别记录状态；只有策略声明的必要目标全部成功后才允许激活。客户端可见版本入口最后更新，发布中途失败时线上客户端继续使用旧版本。

zip 传输对象固定条目名、时间戳、权限位、压缩算法和压缩级别，以保证相同输入产生相同字节。远端验证由存储适配器声明可信哈希能力；不能信任 ETag 时执行回读哈希。未激活版本和孤立 Blob 按配置的保留期回收。

## 12. 可观测性

- 每次构建生成唯一 `build_id`；
- 同时输出结构化 JSON 日志和可读控制台日志；
- 记录任务、平台、构建 ID、耗时和重试次数；
- 输出缓存命中率、产物数量和上传大小；
- Unity 原始日志作为附件保存；
- 所有密钥和签名材料统一脱敏。

## 13. 测试策略

- 单元测试：领域模型、DAG、配置、依赖、Redirect、分包和文件列表；
- 契约测试：SVN、Unity、Jenkins、CDN 适配器；
- Golden 测试：旧客户端协议；
- 集成测试：临时目录和替身外部工具；
- 端到端测试：小型示例工程；
- 故障测试：超时、缓存损坏、上传中断和产物缺失。
- 文档质量测试：扫描 `src/` 和 `tests/` AST，确保每个模块、类、函数和方法都有包含中文的 docstring；详细度另由人工审查职责、参数、返回、异常、约束和副作用。

质量目标：

- `st.build.core` 覆盖率单独不低于 90%；
- `st.build.release` 覆盖率单独不低于 90%；
- 整体覆盖率不低于 80%；
- 格式、静态检查和测试全部通过后才允许发布。
- 中文文档质量检查通过后才允许合并。

覆盖率是辅助指标。真正的发布门槛还包括协议字节级 diff、故障注入和旧客户端解析器端到端验证。

## 14. 迁移验收

建立旧能力矩阵，至少覆盖：

- config、Lua、struct；
- scene、map、story；
- character、LOD、expression、GPU skin；
- shader variant 和 shader bundle；
- particle、texture、UI、audio、video、skill；
- AB 依赖数据库、Redirect、低清合并和分包；
- Android、iOS、Windows 客户端出包；
- IL2CPP、SDK、分支和美术辅助能力。

每项能力依次通过：

1. 使用脱敏后的真实历史输入建立 fixture；
2. 将旧工具复制到隔离工作区，并在输入快照上运行；禁止从原始 `F:` 目录直接启动任何可能写文件的入口；
3. 旧系统和新系统双跑；
4. 对客户端协议文件执行字节级 diff；
5. 使用旧客户端解析器读取新产物；
6. 在隔离 CDN 前缀执行灰度发布；
7. 验证回滚后再替换生产流水线。

无法字节一致的差异必须记录兼容性决策、客户端验证证据和回退方案。

## 16. 运行状态与并发约束

构建和发布采用显式状态机：

```text
PLANNED → RUNNING → VALIDATING → SUCCEEDED
                    ↘ FAILED

PREPARING → UPLOADING → VERIFYING → ACTIVATING → ACTIVE
              ↘ FAILED             ↘ CONFLICTED
```

- manifest、任务状态、缓存条目和发布记录均包含 schema 版本；
- Unity 工作区按 build ID 隔离并使用许可证并发信号量；
- 每个任务声明超时、CPU、内存和磁盘预算；
- 取消操作先停止调度，再终止外部进程并保留可诊断状态；
- 动态任务扩展必须按稳定键排序，产生确定性图；
- 每个逻辑输出路径只能有一个所有者，fan-in 必须由显式聚合任务完成。
- 规划结果必须包含当前图每个节点的不可变 `expected TaskIdentity` 映射，供 Frontier 恢复验证显式比较。

可执行的资源发布 DAG 至少包含：

```text
固定源码版本
  → 各资源构建任务
  → Unity manifest 收集
  → BuildManifest
  → 与基线完整快照合并
  → Redirect 规划与容器生成
  → 分包映射
  → zip/原始传输对象生成
  → 六字段完整文件列表
  → 对象上传与远端校验
  → 版本列表上传
  → 版本入口 CAS 激活
```

低清发布在完整快照合并前显式依赖主版本 BuildManifest。客户端出包显式依赖一个已激活或已验证的 ReleaseBundle。
