## 2. 目标

实现一条能够由 Jenkins 或未来统一编辑器调用的正式版本资源制作流水线，覆盖：

1. 固定 Git 或 SVN 源码 revision；
2. 加载并校验 TOML 构建配置；
3. 分配正式资源版本号；
4. 独立执行十二个资源打包任务；
5. 汇总已明确提交的任务结果并生成确定性 `BuildManifest`；
6. 生成当前阶段需要的旧客户端兼容输出；
7. 制定确定性上传计划；
8. 上传到本地 CDN，或通过未来适配器上传真实 CDN/对象存储；
9. 校验远端内容后以 CAS 原子更新版本入口；
10. 为 Jenkins、人工和 AI 排查提供完整、独立且脱敏的 `.log` 日志。

正式版本制作是端到端用例，但内部必须保持构建产物、运行记录和发布模型分离：

- `BuildManifest` 只记录可复现构建产物；
- `BuildExecutionRecord` 记录 `build_id`、运行状态、耗时和日志；
- `ReleaseRequest` 和 `ReleaseBundle` 记录资源版本、渠道、平台和发布内容；
- `ReleaseActivationRecord` 记录上传、验证、激活、冲突和回滚状态。

### 3.3 Redirect 边界

Redirect 的目的是将零散小包合并到较大的容器中，并以名称、偏移和长度定位原资源。它属于构建完成后的高级布局优化，不属于十二个资源任务。

基础流程为：

```text
原始资源产物 -> Manifest -> 上传 -> 发布
```

未来启用 Redirect 后变为：

```text
原始资源产物
  -> 可选高级布局优化（后续阶段）
  -> 合并容器 + Redirect 索引
  -> 最终 Manifest
  -> 上传 -> 发布
```

纯 Python 发布层已经提供版本化 Redirect 规划、容器 Blob 构建和兼容输出登记；这些能力仍只在
受控输入/对象存储端口中运行，不代表真实历史 CDN 或旧客户端平台验收完成。

Redirect 关闭时不生成 Redirect 行或容器；每个原始 AssetBundle 作为普通条目进入完整快照，并按既有 membership 规则进入文件列表和对应 `assetbundledb_*.txt`。

## 5. 正式版本数据流

完整流程由 Jenkins 或未来编辑器逐步调用：

```text
固定源码 revision
  -> 创建 BuildExecutionContext
  -> 加载并冻结配置快照
  -> 预留 FileListNo
  -> Jenkins 独立调用所需资源任务
  -> 每个任务生成 TaskResult 和独立日志
  -> Jenkins 显式调用 aggregate
  -> 生成 BuildManifest
  -> 创建完整 ReleaseSnapshot
  -> 创建 ReleaseManifest / ReleaseBundle
  -> 从 ReleaseBundle 生成基础兼容输出
  -> 生成确定性上传计划
  -> 上传不可变对象
  -> 校验远端哈希和大小
  -> mark_ready 固化 Bundle、UploadPlan 和远端证明
  -> prepare_activation 固化 CAS 前置条件
  -> CAS 更新版本入口
  -> confirm 确认 FileListNo 已发布
```

构建失败、聚合失败、上传不完整或远端校验失败时，不得更新版本入口。已上传的不可变对象可以保留，用于重试或审计。

正式发布第一期只支持完整发布：`ReleaseCompositionPolicy.required_tasks` 固定为上述十二个任务。单任务和任意任务子集可用于开发验证，但不能直接创建可发布 `ReleaseBundle`。正式聚合必须收到十二个成功结果，构造完整 `BuildManifest`，再从全部产物创建完整 `ReleaseSnapshot`、`ReleaseManifest` 和 `ReleaseBundle`。第一期不使用 baseline 合并局部结果；增量完整快照合并另行设计后才能开放。

### 5.1 外部编排

工具不生成自动资源 DAG，也不推断任务关系。应用层只提供三个主要用例：

```text
ResourceBuildService.build(task_name, request)
ManifestService.aggregate(requested_task_results)
PublishService.publish(release_request, destination)
```

Jenkins Job 通过稳定的 Python 应用门面调用这些服务：

```text
JenkinsJobFacade.run(JenkinsJobRequest) -> JenkinsJobResult
```

`JenkinsJobRequest` 至少包含 `schema_version`、`request_id`、可选 `retry_of`、动作、`build_id`、配置快照 locator、source revision、任务名或结果 locator 集合，以及取消上下文。`request_id` 是一次实际尝试的幂等键，应用门面首次接收时生成 `run_id` 并持久化请求规范摘要：

- 相同 `request_id` 和相同请求摘要重复到达时，不重新执行，返回原 `run_id` 及当前或最终结果；
- 相同 `request_id` 携带不同请求摘要时返回 `REQUEST_ID_CONFLICT`；
- 前一次已失败或取消后需要真正重试时，Jenkins 使用新的 `request_id`、相同 `build_id`，并通过 `retry_of` 引用前一次请求；
- 新尝试生成新的 `run_id` 和日志目录，但版本分配仍按 `build_id` 保持幂等。

应用门面必须先在持久请求注册表中以 CAS 原子认领 `request_id`，再开始副作用；并发重复请求只能观察同一条 `RUNNING` 记录，不能各自启动执行。

持久注册表还必须在首次请求时把 `build_id` 绑定到共享 `BuildContext.request_digest`。后续任务或重试使用相同 `build_id` 但携带不同 revision、工具链、platform、profile 或配置快照时返回 `BUILD_CONTEXT_CONFLICT`，不得执行。

`JenkinsJobResult` 返回 `RUNNING`、`SUCCESS`、`FAILED` 或 `CANCELLED`，并携带 `run_id`、稳定错误码、结果 locator 和日志 locator。

Jenkins 现有 Python Job 脚本直接导入并调用该门面；CLI 只路由固定的资源、正式版本、外部探针
和兼容验收命令，不替人工猜测业务参数。Jenkins 中止 Job 时先设置取消上下文，再由
`ProcessRunner` 终止当前外部进程树；进程被强制终止时，应用门面仍尝试原子写入取消记录和日志，
写入失败则由 Jenkins 归档已有日志并标记基础设施失败。

Jenkins 可以顺序或并行调用任意任务。例如：

```text
Jenkins Pipeline
  -> config
  -> shader_variant
  -> shader_bundle
  -> 并行调用 scene/map/character/texture/ui/particle/audio/video/lua
  -> aggregate
  -> publish
```

上例只是 Jenkins 配置示例，不是工具内置顺序。即使某个任务需要另一个任务生成的数据，也必须由 Jenkins 先执行对应 Job，并将结果路径作为当前任务的显式输入。输入不存在时当前任务失败，不自动触发其他任务。

不同 Jenkins Job 可能运行在不同节点，因此任务交接不能依赖某台节点的临时绝对路径：

- 任务先把产物提交到所有相关 Jenkins 节点可读取的持久内容寻址 Blob 存储；
- 任务将确定性产物清单和运行记录组成版本化 `TaskResultPackage`；
- 结果包先写临时目录，校验完成后原子改名；`result_id` 对两个 TOML 文件按固定名称顺序执行规范 framing 后计算 SHA256。每段 framing 为“8 字节无符号大端文件名长度、UTF-8 文件名、8 字节无符号大端内容长度、规范 TOML bytes”，长度不得超过 UInt64；`result.sha256` 只保存该值且不参与自身摘要；
- Jenkins 通过 archive/stash 或显式结果存储传递结果包；聚合 Job 必须先下载到自己的隔离工作区；
- 聚合 Job 重算 `result_id`、任务清单 ID 和每个 Blob 哈希后，再生成 `BuildManifest`；
- `build_id` 只用于关联多个 Job，不表示它们共享本地目录。

## 6. TOML 配置与编辑器 API

### 6.1 两类配置

本设计区分：

- 构建系统配置：使用 TOML，控制路径、工具、环境、任务和发布策略；
- 游戏配置资源：由 `config.py` 任务生成读取代码、BIN 和可选调试 TXT。

构建配置建议拆分为：

```text
config/
  build.toml
  profiles/
    debug.toml
    release.toml
  environments/
    local.toml
    ci.toml
```

合并顺序固定为：

```text
build.toml + profile TOML + environment TOML = 本次只读配置快照
```

示例：

```toml
schema_version = 1

[project]
name = "se"
source_root = "client"
output_root = "build/output"
temp_root = "build/temp"

[profile.debug]
emit_config_txt = true
compile_lua = false
encrypt_lua = false

[profile.release]
emit_config_txt = false
compile_lua = true
encrypt_lua = true

[tools.unity]
executable = "C:/Program Files/Unity/Editor/Unity.exe"
timeout_seconds = 7200

[version_control]
provider = "svn"
credential = "secret://version-control/build-user"

[object_store]
provider = "filesystem"
destination_id = "local-development"
root = "D:/local-cdn"

[publish.layout]
root_prefix = "{branch}/{platform}/data/{job}"
version_entry_key = "version/{branch}/{platform}/{job}"

[tasks.config]
enabled = true
source = "config"
output = "config"

[tasks.lua]
enabled = true
source = "lua"
output = "script"
```

TOML 中不提供 `depends_on`。任务顺序不属于工具配置。

### 6.2 配置规则

- 配置加载后转换为不可变强类型模型；
- TOML 读写保持稳定字段顺序；
- 路径使用 `pathlib.Path`，客户端逻辑路径统一使用 `/`；
- 未知字段、非法 Profile、缺失工具、输出冲突和越界路径在执行前失败；
- 路径、格式、工具、输出位置、开关、超时、重试和版本规则不得散落硬编码；
- 密码、Token、私钥和加密密钥只能保存为 `SecretRef`；
- 加载或保存配置不会触发 Unity、版本控制或上传操作。

### 6.3 编辑器 API

第一期实现编辑器可调用的纯 Python API，不实现 CLI、桌面 UI 或 Web UI：

```text
BuildConfigService
  load(path) -> BuildConfig
  validate(config) -> ValidationReport
  save(path, config)
  update_task(config, name, task_config) -> BuildConfig
  enable_task(config, name) -> BuildConfig
  disable_task(config, name) -> BuildConfig
  resolve_profile(config, name) -> ResolvedBuildConfig
```

未来编辑器必须通过该服务读写 TOML，不能绕过校验直接拼接文件。
服务不持有隐式当前配置；所有修改 API 都接收不可变配置并返回新值。

## 7. 资源任务契约

所有任务实现统一生命周期：

```text
validate
  -> discover_inputs
  -> discover_outputs
  -> build
  -> verify
  -> collect_artifacts
```

`discover_outputs` 必须是基于固定源码和配置快照的只读、确定性规划过程。在实际执行前枚举精确输出，以继续满足现有 `TaskSpec.outputs` 严格相等约束。禁止使用未校验的输出目录前缀代替精确输出集合。

十二个任务生成的 `TaskSpec.dependencies` 必须全部为空，调用现有 `TaskIdentity.from_plan` 时传入的 upstream identities 也必须为空。Jenkins 顺序不转换为工具内部依赖。任务之间需要传递数据时，调用方显式提供不可变 `InputArtifactRef`；其逻辑路径、BlobRef、SHA256、大小和来源摘要进入当前任务输入树与 `TaskIdentity`，但不进入 `TaskSpec.dependencies`，也不会触发生产该输入的任务。

每个任务直接生成现有 `core.artifacts.LogicalArtifact`，不得创建第二套资源产物模型：

```text
LogicalArtifact
  logical_path
  kind                   # ArtifactKind.ASSET_BUNDLE 或 FILE
  blob                   # BlobRef(locator, sha256, size)
  dependencies           # 保留 Unity Manifest 的有序重复依赖
  subpackage_ids          # 本期固定为空 frozenset()
  metadata               # ArtifactMetadata(source_task, source_revision,
                         #                  toolchain_digest, attributes)
```

`LogicalArtifact.blob` 不保存临时工作区路径作为持久 locator。任务产物必须先经过哈希、大小、逻辑路径、AB dependencies 和输出所有权校验，再登记到内容寻址存储。`dependencies` 是后续完整 `ReleaseSnapshot` 和 `assetbundledb_*.txt` 的唯一依赖来源；即使本期不做分包，也保留现有 `subpackage_ids` 字段并固定为空集合。

| `scene` | 场景、场景依赖、分组规则 | 场景 Bundle、场景索引 | 场景缺失、依赖错误、Unity 无产物 |
| `map` | 地图数据、地图资源引用 | 地图数据包、地图索引 | 地图配置错误、引用缺失、输出污染 |
| `character` | 角色 Prefab、模型、动画、材质引用 | 角色 Bundle、角色索引 | 资源引用错误、Unity 失败、输出冲突 |
| `texture` | 独立贴图、公共贴图、压缩规则 | 贴图 Bundle、贴图索引 | 格式或压缩规则错误、重复逻辑路径 |
| `ui` | UI Prefab、图集、字体、UI 贴图 | UI Bundle、图集与 UI 索引 | 图集或字体输入错误、重复输出 |
| `particle` | 粒子 Prefab、材质、贴图引用 | 粒子 Bundle、粒子索引 | 依赖缺失、Unity 失败、未声明输出 |
| `audio` | 音频源、bank 列表、编码规则 | 音频包、音频索引 | bank 缺失、大小写冲突、编码失败 |
| `video` | 视频源、编码或复制规则 | 视频包、视频索引 | 重名、格式不支持、复制或编码失败 |
| `lua` | Lua 源码、排除规则、编译和加密配置 | Lua 包、脚本索引 | 编译失败、加密失败、密钥泄漏风险 |

### 7.2 `config` 任务

`config.py` 必须生成配置读取代码和运行时 BIN：

```text
Debug   -> 读取代码 + BIN + TXT
Release -> 读取代码 + BIN
```

Debug TXT 仅用于排查。读取代码和 BIN 必须来自同一个 Schema 快照。旧分包映射检查从该任务中删除。

### 7.3 `lua` 任务

Lua 支持三种配置模式：

```text
source    -> 原始 Lua 文件打包
bytecode  -> 编译后打包
encrypted -> 源码或字节码处理后加密打包
```

编译器、加密器、Lua 版本和规则均从配置及工具端口获得。Release 使用哪种模式由项目配置决定，任务本身不写死算法或工具路径。

### 7.4 聚合

每个任务输出一个版本化 `TaskResultPackage`：

```text
TaskResultPackage
  task-artifact-manifest.toml
  task-execution-record.toml
  result.sha256
```

确定性 `TaskArtifactManifestPayload` 包含：

```text
schema_version
build_context
  schema_version
  request_digest
  revision
  toolchain_digest
  baseline_id             # 第一版正式全量构建必须为 None
task_plan
  spec.name
  spec.dependencies       # 十二个任务必须为 ()
  spec.outputs
  spec.implementation_version
  spec.execution_attributes
  resolved_input_digest
  config_digest
task_identity
explicit_input_digests    # 用于审计，且必须已包含在 resolved_input_digest 中
artifacts
```

`TaskArtifactManifestFactory` 对规范 payload 重算不可变 `manifest_id`。读取结果时必须从 payload 重建现有 `TaskSpec`、`TaskPlan` 和 `BuildContext`，以空 upstream identities 调用现有 `TaskIdentity.from_plan` 重算身份，并验证实际 artifacts 逻辑路径集合严格等于 `spec.outputs`。无法重建、身份不符、outputs 不符或非空 dependencies 均拒绝。

所有 Job 使用同一个正式构建请求快照，因此 `BuildContext.request_digest` 是该共享请求的摘要，不是单个 Jenkins 调用的 `request_id`。platform 和 profile 必须进入共享 request digest；任务自己的已解析配置进入 `TaskPlan.config_digest`。

运行态 `TaskExecutionRecord` 单独包含 `build_id`、`run_id`、`request_id`、状态、开始/结束时间、耗时、日志 locator、诊断 locator 和对应 `manifest_id`。渠道、发布版本、CDN 目标和凭据不得进入 `TaskArtifactManifestPayload`。

`aggregate` 只消费 Jenkins 明确传入的结果包，不扫描目录猜测任务，不补齐遗漏任务，也不自动启动任务。它要求运行记录为 `SUCCESS`，重算所有结果身份，并要求十二项的 `BuildContext` 中 schema、request digest、revision、toolchain digest 和 baseline 全部一致。聚合器把这些公共字段、全部逻辑产物和按任务名稳定排序的 `TaskIdentity.digest` 写入现有 `BuildManifestPayload`，最后只通过 `BuildManifestFactory` 重算 `manifest_id`。`TaskExecutionRecord` 中的 `build_id`、`run_id`、状态、时间和日志不得复制到 `BuildManifestPayload`。

聚合必须拒绝：

- 共享 `BuildContext` 的 schema、request digest、source revision、toolchain digest 不一致，或正式全量构建的 baseline 不为 `None`；
- 重复逻辑路径；
- 缺失或未声明产物；
- 文件哈希、大小或 Blob locator 不一致；
- 未完成或失败的任务结果。

十二项的 `TaskPlan.config_digest` 允许不同，因为每个任务只摘要自己的已解析配置子集；聚合只需按各自完整 `TaskIdentity` 重算并验证。platform、profile 和完整配置快照身份通过所有任务共享的 `BuildContext.request_digest` 保证一致。

开发聚合可以显式选择任务子集并生成不可发布的开发 `BuildManifest`。正式版本聚合必须根据 `ReleaseCompositionPolicy` 验证十二个任务恰好各有一个成功结果；缺少或多出任务均不得进入发布组装。

## 8. 工作区、缓存和重试

### 8.1 工作区隔离

```text
work/{build_id}/{task_name}/{run_id}/
  input/
  temp/
  output/
  result/
    task-artifact-manifest.toml
    task-execution-record.toml
    result.sha256
  logs/
```

- 每个任务和每次重试使用独立目录；
- 任务只允许修改自身运行目录和明确授权的 Unity 输出目录；
- 临时产物验证通过后再原子提交到最终输出；
- 失败现场默认保留；
- 清理只能针对解析并验证后的具体 `build_id/task_name/run_id` 目录。

### 8.2 缓存

缓存指纹至少包含：

```text
task_name
task_implementation_version
source_revision
input_file_hashes
resolved_config_digest
platform
profile
Unity/tool versions
explicit_external_inputs
```

缓存命中后仍须验证 Manifest、文件大小和内容哈希。损坏缓存不得返回业务层，应记录警告并重新构建。缓存按内容与任务身份复用，不使用 `build_id` 作为内容身份。

### 8.3 重试和幂等

Jenkins 决定是否重试完整资源任务，工具不递归重启完整任务。Unity 失败、配置错误、Git/SVN 写操作和产物校验失败默认不自动重试。

允许有限重试的操作只有明确的临时故障，例如 Jenkins 状态查询和对象上传。所有重试必须记录次数、原因和最终结果。

幂等规则：

- 相同任务输入和指纹产生相同逻辑产物；
- 相同哈希对象重复上传时跳过；
- 相同 FileListNo、相同 `ReleaseBundle` ID、相同 `UploadPlan.plan_id` 且 replacement 入口规范字节相同的重复发布视为幂等成功；
- 相同 FileListNo 但 `ReleaseBundle` ID、`UploadPlan.plan_id` 或 replacement 入口摘要任一不同，均禁止覆盖；
- 版本入口只能通过 CAS 更新。

## 9. 版本号、上传和发布

### 9.1 版本号

```text
VersionAllocator
  preview
  allocate
  mark_ready
  prepare_activation
  confirm
  reconcile
  abandon
```

版本规则由 TOML 配置，例如：

```toml
[version]
display_format = "{major}.{minor}.{file_list_no}"
major = 1                       # 仅用于人工显示
minor = 0                       # 仅用于人工显示
counter = "jenkins_build_number"
```

客户端资源版本以 `FileListNo` 为唯一协议值，范围是 `1..Int32.MAX_VALUE`。`1.0.1052` 之类的显示版本只用于 Jenkins、编辑器和日志，不进入六字段文件列表、`object_version` 或客户端版本入口。main 本次新上传对象的 `object_version` 严格等于十进制 `FileListNo`，例如 `1052`。

本地模式使用带进程间锁和 CAS 的持久计数器；Jenkins 模式可以建议使用 Jenkins build number，但仍必须经过版本存储的唯一性校验。重复、非正数、超过 Int32、已被其他 `build_id` 占用或小于已发布高水位的号码全部拒绝。

版本流不按 channel/platform 直接分区，而是由最终 CAS 入口唯一确定：

```text
version_stream_id = SHA256(canonical_json_bytes([
  destination_id,
  object_store_namespace,
  normalized_version_entry_key
]))
```

`destination_id` 是不含凭据的稳定目标标识；filesystem namespace 使用解析后的存储根身份，远端适配器使用稳定 bucket/container namespace。相同物理入口必须生成相同 `version_stream_id`，不同入口必须不同。channel、platform、branch 和 job 只参与布局配置，最终都归一到实际 entry key 后再计算流身份。

版本存储按 `version_stream_id` 保存永不因回滚降低的 `published_high_watermark`。版本预留记录至少包含 `version_stream_id`、`reservation_id`、首次 `request_id`、`build_id`、`file_list_no`、显示版本、状态、`ReleaseBundle` ID、确定性 `UploadPlan.plan_id`、远端验证证明 locator/摘要、预期入口 generation、预期入口摘要、replacement 入口摘要、replacement 规范字节 BlobRef 和时间。状态机为：

```text
RESERVED
  -> READY              # ReleaseBundle 和全部远端对象已验证
  -> ACTIVATING         # 已持久化目标 Bundle 与 expected generation
  -> PUBLISHED          # 入口 CAS 已确认指向目标 Bundle

RESERVED/READY -> ABANDONED
ACTIVATING -> CONFLICTED
```

`allocate(build_id, request_id)` 按 `build_id` 幂等：同一正式构建的不同 Jenkins 重试请求都返回同一个 reservation，不消耗新号码；不同构建并发分配必须得到不同单调号码。号码一旦持久化就不得复用。

`mark_ready(reservation_id, release_bundle_id, upload_plan_id, verification_proof)` 是唯一 `RESERVED -> READY` 入口。它验证 `UploadPlan` 已包含 ReleaseBundle、全部基础兼容输出、文件列表、版本描述和所有待上传资源，且远端证明逐项覆盖该计划中的 object key、SHA256 和大小；证明的 `plan_id` 必须与请求一致。字段完全相同的重复调用幂等成功，任一身份不同则冲突。

`prepare_activation` 在 CAS 前重新读取当前入口和 `published_high_watermark`：FileListNo 相同且入口已指向同一 Bundle 时返回幂等成功；其他小于或等于当前入口 FileListNo，或小于或等于历史高水位的正常激活全部拒绝。通过单调性检查后，原子写入目标 Bundle、expected generation、expected digest、replacement digest 和 replacement 规范字节 BlobRef。CAS 后的 `confirm` 幂等地核对客户端入口，把状态转为 `PUBLISHED`，并以 max 语义推进持久高水位。

若进程在 CAS 前崩溃，`reconcile` 使用预留记录中的完整 CAS 前置条件读取入口：generation 和摘要均匹配时可以提交完全相同的 replacement；任一字段被其他发布改变则转为 `CONFLICTED`。若进程在 CAS 成功后、`confirm` 前崩溃，`reconcile` 发现入口规范字节摘要和 Bundle 均等于 replacement 后补记 `PUBLISHED`。因此客户端入口和版本存储不会因最后一步失败而永久分裂。`abandon` 只适用于尚未进入 `ACTIVATING` 的预留；废弃号码保留审计且不复用。

回滚不经过正常 `allocate/prepare_activation`，由独立 `ReleaseRollbackService` 执行。它必须显式指定已验证的历史 `ReleaseBundle`、操作者授权和 expected generation，允许 FileListNo 降低，并生成独立回滚审计记录；普通发布路径绝不允许版本倒退。

状态字段要求：`RESERVED` 不得包含 Bundle、plan、远端证明或 CAS replacement；`READY` 必须包含已验证 Bundle、`UploadPlan.plan_id` 和覆盖全部必要对象的远端证明；`ACTIVATING` 还必须包含 generation、expected/replacement 摘要和 replacement BlobRef；`PUBLISHED`、`ABANDONED`、`CONFLICTED` 为不可逆终态。未知状态或缺少当前状态必需字段的记录必须拒绝加载。

### 9.2 对象存储与本地 CDN

统一端口：

```text
ObjectStore
  stat
  read
  put_if_absent
  compare_and_swap
  verify_hash
  list
```

第一期实现：

- `FileSystemObjectStore`：以本地目录实现完整发布语义，作为本地 CDN；
- `MemoryObjectStore`：自动化测试使用；
- 确定性上传计划；
- 哈希和大小验证；
- 幂等写入；
- CAS 版本入口。

不引入 `boto3`、腾讯 COS SDK 或其他供应商依赖。未来只增加对应 `ObjectStore` 适配器和配置，不修改资源任务与发布领域逻辑。

`ObjectKey` 必须是使用 `/` 的受约束相对路径，禁止空值、绝对路径、Windows 盘符、UNC、反斜杠、空路径段、`.`、`..`、控制字符和 URL 转义绕过。同一上传计划中大小写折叠后相同的 key 视为冲突。

`put_if_absent` 接受预期 SHA256 和大小：key 不存在时写入并返回 `CREATED`；已存在且内容完全相同时返回 `ALREADY_PRESENT`；已存在但摘要或大小不同则返回 `CONTENT_CONFLICT`，禁止覆盖。`compare_and_swap` 接受 entry key、expected generation、expected content digest 和 replacement，返回 `APPLIED`、`UNCHANGED` 或携带当前 generation/digest 的 `CONFLICT`。

`FileSystemObjectStore` 在每次读写前解析并确认最终路径仍位于配置根目录内，逐级拒绝符号链接、junction 和其他 reparse point。不可变对象上传必须使用逐 key 进程间锁或平台原生 no-replace 提交：先写同目录唯一临时文件并 flush，再以“目标不存在才成功”的原子操作提交，禁止使用会覆盖目标的 replace。竞争失败后重新读取现有对象；内容一致返回 `ALREADY_PRESENT`，否则返回 `CONTENT_CONFLICT`。入口 CAS 单独使用进程间锁和原子替换。验证器不能只信任上传响应或文件元数据，必须从目标存储读取内容或可信供应商校验和并重新确认大小和哈希。

本地 CDN 必须复现既有客户端布局，不使用另一个 `current.json` 协议。示例：

```text
D:/local-cdn/{branch}/{platform}/data/{job}/
  1052/
    scene/main.assetbundle
    config/runtime.bin
    1052.txt.zip
  {configured_version_entry}
```

协议映射固定为：

- `FileListNo = 1052`；
- 本次 main 新对象 `object_version = "1052"`；
- `FileUrl = quote(f"1052/{logical_path}", safe="/")`，压缩对象按旧协议追加 `.zip`；
- 完整文件列表位于 `1052/1052.txt.zip`；
- 资源根布局为 `{root}/{branch}/{platform}/data/{job}/{object_version}/{FileName}`；
- 配置指定的客户端版本入口最后更新 `FileListBaseUrl` 和 `FileListNo`；
- 入口对象 key 必须由 `[publish.layout].version_entry_key` 显式配置；缺失即校验失败；
- 版本化兼容布局策略生成入口内容并固定 `FileListBaseUrl`、`FileListNo`、编码和更新顺序，Golden fixture 验证目标环境的具体 key 与字节；业务代码不得写死 `current.json`。

### 9.3 发布顺序

`UploadPlan` 是确定性不可变计划，至少包含 `ReleaseBundle` ID、按 object key 稳定排序的必要对象 `(key, sha256, size, role)`、全部兼容输出、版本描述和 replacement 入口摘要。工厂对规范 payload 计算 `plan_id`。同一个 Bundle 因布局、压缩或兼容输出不同而得到不同 `plan_id`，发布幂等和远端验证均以该 ID 为准。

1. 生成确定性上传计划；
2. 上传版本目录下的不可变资源对象；
3. 校验每个对象的大小和哈希；
4. 上传 Manifest 与版本描述；
5. 验证版本完整性；
6. 调用 `mark_ready` 固化 Bundle、UploadPlan 和远端证明；
7. 调用 `prepare_activation` 固化入口 CAS 的 expected/replacement 内容；
8. 最后以 CAS 更新配置指定的客户端版本入口中的 `FileListBaseUrl` 和 `FileListNo`；
9. CAS 冲突时保持旧入口并返回明确冲突；
10. CAS 成功后调用 `confirm`，失败恢复使用 `reconcile`；
11. 回滚只切换到已验证的历史版本，不删除不可变对象。

## 10. 外部端口和真实适配器

### 10.1 进程执行

所有外部命令经过 `ProcessRunner`：

- 使用参数数组，不拼接 shell 字符串；
- 控制工作目录、环境变量、超时和取消；
- 捕获并实时转发 stdout、stderr；
- 返回退出码和耗时；
- 对命令和环境中的敏感信息脱敏；
- 取消时终止完整进程树。

### 10.2 Unity

`UnityBatchAdapter` 接受强类型请求，再生成真实 Unity batchmode 命令。资源任务不直接拼接 `-batchmode`、`-executeMethod` 或旧 `-BUILD_*` 参数。

适配器必须保存 Unity 完整日志，检查退出码、超时、预期输出和 Unity 结果标记。具备 Unity 环境后才能完成真实平台验收。

### 10.3 Git 和 SVN

读取和写入能力分离：

```text
VersionControlReader
  resolve_revision
  materialize
  update
  status
  diff

VersionControlWriter
  add
  delete
  commit
  push
  create_branch
  create_tag
```

实现真实 `GitCliAdapter` 和 `SvnCliAdapter`。SVN 没有独立 push 时，适配器在 commit 成功后返回已发布状态；SVN branch/tag 使用 repository copy。所有写操作必须显式调用、携带预期 revision，并记录脱敏审计日志。普通资源任务不得隐式执行版本控制写操作。

### 10.4 Jenkins

Jenkins 是十二个资源任务的主要外部编排者。工具内部不复制 Jenkins 的排序和并行逻辑。

同时实现 `JenkinsClient`，供未来编辑器触发、查询和取消 Job：

```text
trigger_job
get_queue_status
get_build_status
cancel_queue_item
cancel_build
```

客户端支持 Token 引用、CSRF crumb、超时、有限重试和队列 ID 到构建 ID 的转换。凭据不得进入日志。

这里的 `JenkinsClient` 是系统或未来编辑器主动触发 Jenkins 的出站适配器；第 5.1 节的 `JenkinsJobFacade` 是 Jenkins Job 调用构建系统的入站应用边界。两者方向相反，不得互相替代。

```text
      publish_20260815_151000_01915f3e.log
```

目录规则为 `logs/{build_id}/{task_name}/{run_id}/`，文件名规则为 `{task_name}_{启动时间}_{run_id}.log`。`run_id` 是每次应用服务实际执行时生成的不可重复 UUID。真正重试使用新的 `request_id` 和 `run_id`、相同 `build_id`，并通过 `retry_of` 关联前一次尝试；同一 `request_id` 的重复投递不创建新日志。外部日志在同一基础名后追加 `_stdout`、`_stderr` 或 `_unity`。创建日志文件时使用排他创建，发生碰撞立即失败，禁止覆盖旧日志。

### 11.2 显示级别

```toml
[logging]
console_level = "INFO"
file_level = "DEBUG"
show_traceback = true
capture_process_output = true
root = "logs"
retain_days = 30
```

- Jenkins 控制台实时显示 `INFO`、`WARNING` 和 `ERROR`；
- 任务 `.log` 默认保存完整 `DEBUG` 信息；
- 本地调试可以把控制台级别切换为 `DEBUG`；
- 错误始终输出稳定错误码、上下文、诊断文件路径和异常调用链；
- 外部程序 stdout、stderr 和 Unity Editor 日志单独保存。

统一单行格式：

```log
2026-08-15 14:30:35.247 [ERROR] build_id=build-1052 task=scene step=unity error_code=UNITY_PROCESS_EXIT_NONZERO exit_code=1 message="Unity 执行失败"
```

`build.log` 只汇总全局流程、任务状态和各任务日志位置。失败时在 Jenkins 控制台和任务日志末尾输出根因摘要。

不同 Jenkins 节点不得并发追加同一个 `build.log`。每个 Job 只写自己的任务日志并归档；最终聚合或发布 Job 根据显式日志引用一次性生成本次 `build.log`，写入过程同样使用临时文件和原子替换。

`retain_days` 仅供独立维护任务使用。清理器必须取得日志根目录维护锁，跳过存在活跃 lease、未完成发布、未成功归档或保留标记的运行；只删除已归档且超过期限的精确 run 目录。归档或删除失败只记录维护错误，不得改变构建/发布状态。

### 11.3 必须记录的事件

- 服务和任务开始、成功、失败、取消和耗时；
- 配置来源、Profile、配置摘要和 source revision；
- 输入数量、计划输出数量、实际产物数量；
- 脱敏后的外部命令、工作目录、退出码和原始日志位置；
- Unity、Git、SVN、Jenkins 和对象存储操作结果；
- 缓存命中、失效、损坏和重新构建；
- 上传计划、跳过、上传、哈希校验和 CAS 结果；
- Manifest、版本号和发布入口变化；
- 重试次数、取消、超时和异常调用链。

密码、Token、Cookie、Authorization Header、含凭据 URL、私钥和 Lua 加密密钥不得写入任何日志。

## 12. 错误模型

所有外部和业务失败转换为稳定错误码：

```text
CONFIG_VALIDATION_FAILED
REQUEST_ID_CONFLICT
BUILD_CONTEXT_CONFLICT
SOURCE_REVISION_NOT_FOUND
PROCESS_TIMEOUT
PROCESS_CANCELLED
UNITY_PROCESS_EXIT_NONZERO
TASK_INPUT_MISSING
TASK_OUTPUT_MISSING
TASK_UNDECLARED_OUTPUT
ARTIFACT_HASH_MISMATCH
RESULT_PACKAGE_INVALID
MANIFEST_AGGREGATION_FAILED
RELEASE_TASK_SET_INCOMPLETE
VERSION_ALLOCATION_FAILED
VERSION_RESERVATION_CONFLICT
OBJECT_KEY_INVALID
OBJECT_UPLOAD_FAILED
REMOTE_VERIFICATION_FAILED
PUBLISH_CAS_CONFLICT
INTERNAL_ERROR
```

`INTERNAL_ERROR` 只用于未被稳定业务错误码覆盖的意外内部失败。异常类型本身不决定唯一错误码：
`ConfigurationError` 映射 `CONFIG_VALIDATION_FAILED`；其他 `BuildError` 必须由抛出场景显式提供
本节已有的稳定错误码，缺少场景码时映射 `INTERNAL_ERROR`；未知异常同样映射
`INTERNAL_ERROR`。持久失败记录只保存脱敏后的有限深度 cause 描述，不序列化异常对象或完整
traceback；进程内日志可以单独记录经脱敏的调用链。

错误结果包含：

```text
BuildFailure
  error_code
  message
  build_id
  task_name
  step_name
  retryable
  cause
  diagnostic_paths
  context
```

配置和输入错误在调用 Unity 前失败。输出缺失、未声明输出和哈希错误不得进入 Manifest。任一正式版本必需步骤失败都不得更新 CDN 版本入口。

## 13. 测试与验收

### 13.1 自动化测试

- 配置层：TOML 加载、合并、稳定写回、未知字段和 `SecretRef`；
- 日志层：独立命名、并行隔离、级别、stdout/stderr、调用链和凭据脱敏；
- 进程层：真实 stdout、stderr、退出码、超时、取消和参数转义；
- Git：临时仓库中的 status、diff、add、delete、commit、push、branch 和 tag；
- SVN：环境可用时使用临时本地仓库验证对应操作，缺少工具时记录明确跳过原因；
- Jenkins：本地 HTTP 测试服务器验证鉴权、crumb、触发、轮询、取消和错误响应；
- Jenkins 应用门面：请求 schema、同 ID/同摘要复用原 run、同 ID/异摘要冲突、新 ID 重试、build ID/BuildContext 绑定、并发原子认领、取消传播、稳定结果状态和跨 Job 结果交接；
- Unity：假 Unity 契约测试，具备环境时运行隔离 fixture 冒烟测试；
- ObjectStore：路径逃逸、盘符/UNC、大小写冲突、reparse point、异内容冲突、幂等写入、哈希验证和 CAS 冲突；
- 十二个任务：空 dependencies、显式输入身份、成功、缺输入、工具失败、输出污染、取消和确定性；
- 结果交接：schema、原子写入、结果包摘要、持久 Blob、跨节点下载、运行记录隔离和重试幂等；
- 版本预留：version stream 映射、Int32 边界、历史高水位、并发、重复 Jenkins build number、mark_ready 证明覆盖、UploadPlan 身份、崩溃点、废弃、重复 confirm 和 reconcile；
- 日志保留：run ID 碰撞、单写者、活动 lease、归档失败和清理失败；
- 发布：完整十二任务门禁、BuildManifest 到 ReleaseSnapshot/Manifest/Bundle、兼容输出、本地 CDN 上传、校验、激活、重复发布和失败恢复。

### 13.2 专项验收

`config`：

- Debug 生成读取代码、BIN 和 TXT；
- Release 生成读取代码和 BIN；
- 读取代码和 BIN Schema 一致；
- 不再生成或检查旧分包映射。

`lua`：

- source、bytecode 和 encrypted 模式分别覆盖；
- 排除规则确定生效；
- 编译或加密失败保留完整日志；
- 日志中不存在加密密钥；
- 相同输入和模式生成稳定产物。

正式发布：

1. 十二个任务均可单独调用，不自动触发其他任务；
2. 每个任务生成独立 `TaskResultPackage` 和 `.log`；
3. 开发聚合只使用显式传入的结果，正式聚合强制十二个任务完整；
4. 依次生成确定性 BuildManifest、完整 ReleaseSnapshot、ReleaseManifest、ReleaseBundle 和基础客户端兼容输出；
5. 上传本地 CDN 并验证所有对象；
6. 完整验证后才更新版本入口；
7. 中途失败时旧入口保持不变；
8. 相同内容重复发布幂等；
9. 相同版本不同内容拒绝覆盖；
10. 人工或 AI 只依靠归档日志即可定位失败阶段、根因和原始诊断文件。

旧协议使用 Golden 测试覆盖本阶段实际生成的 AssetBundle 相对路径、`assetbundledb_*.txt`、六字段文件列表和 CDN 版本目录语义。Redirect 和分包兼容测试不属于本期。

### 13.3 真实环境门禁

替身测试通过不代表真实外部环境已验收。只有完成以下证据后，才能声明对应能力可用：

- 隔离 Unity fixture 的真实构建日志和产物哈希；
- Git/SVN 受控测试仓库的读写操作记录；
- Jenkins 测试 Job 的触发、状态和取消记录；
- 本地 CDN 完整上传、验证、激活和回滚记录；
- 旧系统隔离副本与新实现对同一输入快照的差异报告；
- 旧客户端解析验证。

## 14. 分层实施顺序

书面规格通过用户复核后，另行编写精确的 TDD 实施计划。计划必须按以下层次推进：

1. 配置、日志、错误模型和真实进程执行；
2. Git/SVN、Unity、Jenkins、Secrets 和 ObjectStore 端口及适配器；
3. 资源公共模型、精确输出发现、校验、缓存和单任务执行服务；
4. 十二个具体资源任务；
5. 版本分配、正式十二任务聚合、完整 ReleaseSnapshot/Manifest/Bundle 组装；
6. 当前范围内的旧客户端基础兼容输出；
7. 上传计划、本地 CDN、远端验证、CAS 激活、reconcile 和显式回滚；
8. 真实环境探针、旧系统隔离双跑和迁移证据；
9. 后续独立实施小包合并与 Redirect。

第 5 层只能生成待发布模型，不提供可激活路径。只有第 6 层兼容输出加入完整必要对象集合后，第 7 层才能实现并开放激活，防止缺少六字段文件列表或 `assetbundledb_*.txt` 时发布客户端不可用版本。

每一层必须先写失败测试，再实现最小代码，并通过目标测试、完整测试、覆盖率、Ruff、Pyright、compileall 和中文文档质量检查。未经用户明确要求不得创建 Git commit。
